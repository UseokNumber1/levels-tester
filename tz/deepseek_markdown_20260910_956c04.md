# ТЗ «HourBounce Replay» v2.0 — основное

## 1. Назначение и рамки

Система берёт **готовые** сигналы «отскок от часового уровня» из внешней
архивной БД, прогоняет каждый через движок реплея по правилам
**3 типов входа × 3 размеров стоп-лосса** и отображает результат как матрицу
**3×3 = 9 свечных графиков M5** с полной разметкой событий
(касание → подтверждение → вход → выход).

Система **не ищет сигналы**, а ревьюит уже отработанные. «Не было входа»
и «расхождение с архивом» — такие же полноценные результаты, как TAKE и STOP,
и обязаны отображаться.

**Стек (фиксирован):**
- Frontend: React 18 + TypeScript + TradingView Lightweight Charts v5,
  Vite, Zustand, Tailwind (тёмная тема).
- Backend: Python 3.11+, FastAPI, Pydantic v2, SQLAlchemy 2, Alembic.
- БД: PostgreSQL 15+.
- Котировки: Binance Futures USDT-M REST (`/fapi/v1/klines`).
- Деплой: docker-compose.

**Вне рамок v1:** реальная торговля, алерты, мультипользовательский режим,
сравнение версий конфигурации, полная история котировок, авторизация.

## 2. Термины

| Термин | Определение |
|---|---|
| Сигнал | запись архива: `symbol`, `dt_place`, `level_price`, `side` (BUY — отскок вверх от поддержки, SELL — зеркально), архивные TP/SL, `daily_volume`, `natr` |
| Касание (touch) | первая свеча M5 после `dt_place`, у которой `low <= level` (BUY) / `high >= level` (SELL) |
| Подтверждающая свеча | свеча **строго после** касания, закрытая за уровнем в сторону сделки: `close > level` (BUY) / `close < level` (SELL) |
| T1 — вход по касанию | маркет в момент касания, цена = `level`; при гэпе (open за уровнем) — цена = `open` |
| T2 — после 1-й закрытой | вход по `open` свечи, следующей за 1-й подтверждающей |
| T3 — после 2-х закрытых | вход по `open` свечи, следующей за 2-й подтверждающей |
| S1 / S2 / S3 | три размера стопа в % от цены входа: 0.5 / 1.0 / 1.5 |
| Исходы | `TAKE`, `STOP`, `NO_ENTRY`, `EXPIRED` |

## 3. Правила движка

**3.1.** Сканирование начинается со свечи `dt_place`, окно анализа ограничено
`life_window_t`.

**3.2.** Нет касания → `NO_ENTRY`, `reason = no_touch`.

**3.3.** Подтверждающие свечи ищутся строго после свечи касания.
Свеча касания подтверждением **не считается**, даже если закрылась за уровнем.

**3.4.** Для T2/T3: если за `confirm_window_w = 20` свечей набралось меньше
1 / 2 подтверждающих → `NO_ENTRY`, `reason = no_confirm`.

**3.5.** SL = цена входа ∓ `sl_size%`. Проверка на каждой свече после входа
по `low` (BUY) / `high` (SELL).

**3.6.** TP — трейлинг. Активация: цена достигла
`entry × (1 + tp_trail_activate_pct)` (BUY; для SELL зеркально).
С момента активации трейлинг-линия = `peak × (1 − tp_trail_distance_pct)`
и **только подтягивается**, никогда не откатывается.

**3.7.** Внутри свечи порядок проверок: **сначала стоп, затем активация**.
Подтяжка трейлинга, выполненная на свече N, вступает в силу **со свечи N+1**
(интрасвечная последовательность неизвестна — консервативное допущение).
Гэп через трейлинг-линию → выход по `open`, исход `TAKE`.
Гэп через стоп → выход по `open`, исход `STOP`.

**3.8.** Если на одной свече задеты и стоп, и трейлинг-линия → `STOP`,
результат помечается `ambiguous = true`.

**3.9.** Ни стоп, ни трейлинг не сработали за `life_window_t` → `EXPIRED`.

**3.10.** Каждое событие пишется в цепочку `events[]`
(`seq`, `type`, `dt`, `price`) — из неё строятся и маркеры на графике,
и степпер 1→2→3→4.

**3.11.** Реплей детерминирован: `(signal, config_version)` → идентичный
результат. Результаты кешируются в `replay_results` с привязкой
к `config_version`.

## 4. Архитектура

### 4.1. Компоненты
- `SignalArchiveRepo` — чтение сигналов из внешней архивной БД
  (только SELECT); схема архива известна исполнителю, интерфейс
  изолирует движок и UI от схемы источника.
- `CandleFetcher` — догрузка котировок M5 с Binance Futures по требованию (4.4).
- `ReplayEngine` — чистый модуль без побочных эффектов (см. файл 03).
- `ReplayJobRunner` — фоновый пересчёт матриц при смене конфигурации,
  прогресс-статус.
- REST API (файл 02), Frontend (файл 03).

### 4.2. Подключения к БД
`archive_ro` (внешняя архивная, read-only) и `main` (PostgreSQL).
Миграции Alembic — только для `main`.

### 4.4. CandleFetcher
`GET /fapi/v1/klines` (interval=5m), пагинация по 1500 свечей, учёт
weight-limits, ретрай с экспоненциальным бэкоффом. Загружается только окно,
необходимое для отрисовки:
`[dt_place − pre_candles … max(exit_dt) + post_candles]`; запись идемпотентна
по PK; полная история не хранится. Список символов приходит из архива.

## 5. Нефункциональные требования

- Отрисовка матрицы 9 графиков ≤ 2 с после выбора сигнала (кеш срезов
  свечей и `replay_results`).
- Пересчёт выборки до 5 000 сигналов × 9 комбинаций — фоновым job
  с инкрементальной обработкой только изменённых комбинаций.
- Ровно один instance Lightweight Charts на карточку, destroy при unmount;
  виртуализация матрицы не требуется (9 ячеек).
- Покрытие `ReplayEngine` unit-тестами ≥ 90 %.
- Alembic-миграции, seed-скрипт демо-набора сигналов и котировок,
  `docker-compose up` = рабочее состояние, healthcheck backend,
  логирование job'ов.

Обязательные unit-кейсы движка:
- нет касания → `NO_ENTRY(no_touch)`;
- подтверждение на 21-й свече при W=20 → `NO_ENTRY(no_confirm)`;
- свеча касания закрылась за уровнем → НЕ считается подтверждением;
- TP-трейлинг и SL в одной свече → `STOP` + `ambiguous=true`;
- активация трейлинга по high, срабатывание только со следующей свечи;
- активация и касание SL в одной свече → `STOP`;
- гэп через трейлинг-линию → `TAKE` по open; гэп через стоп → `STOP` по open;
- трейлинг не активировался → `STOP`/`EXPIRED`, `trail_path` пуст;
- T1 с гэпом за уровнем → вход по open, SL считается от open.

## 7. Открытый вопрос к заказчику (до старта этапа 2)

При `tp_trail_activate_pct = 1.0` и `tp_trail_distance_pct = 1.0` трейлинг
в момент активации встаёт на `entry × 1.01 × 0.99 = entry × 0.9999`, то есть
ровно в безубыток. Фактически любой откат после +1 % даёт выход в ноль,
в отчёте будет много TAKE с `R ≈ 0.00`. Варианты:

- `distance = 0.5 %` → при активации фиксируется +0.5 %;
- активация по `+1 %`, трейлинг от **цены входа** до достижения `+2 %`;
- оставить как есть, трактовать TAKE с `R≈0` как «замок».

Решение фиксируется в `payload` активной `config_version` и правится без
redeploy.
