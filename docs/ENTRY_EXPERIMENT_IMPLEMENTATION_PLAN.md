# ТЗ: эксперименты со входом по отскоку

## 1. Назначение документа

Этот документ является рабочим заданием для реализации следующего этапа
`levels-tester`. Он описывает не только проверку факта входа, но и полный
эксперимент по оценке торгового результата.

Цель этапа:

> определить, какие параметры входа по отскоку и какие комбинации стоп-лосса и
> тейк-профита дают положительный и устойчивый совокупный результат на одном и
> том же наборе исторических сигналов.

Кодер не должен менять определение стратегии, SL/TP или метрику по своему
усмотрению. Все решения, перечисленные ниже как обязательные, должны быть
зафиксированы тестами.

## 2. Смысл эксперимента

Один исторический replay должен пройти общий путь:

```text
H1 candles
  -> confirmed level
  -> touch
  -> bounce confirmation on M1/M5
  -> common entry
  -> independent execution variants
  -> SL/TP result
  -> aggregate statistics
```

Ключевое правило сравнения:

- уровни, касания, подтверждения и время входа общие для всех вариантов;
- каждый вариант получает независимую виртуальную сделку;
- результат одного варианта не изменяет состояние другого;
- повторный запуск с теми же данными и конфигурацией даёт тот же результат.

Нельзя запускать отдельный поиск уровней для каждого SL/TP-варианта: это будет
сравнение разных наборов сигналов, а не сравнение управления сделкой.

## 3. Обязательный scope первой версии

В первую версию входят:

- методы подтверждения 1 (`touch`), 3 (`consecutive`) и 5 (`bounce`);
- общий вход `confirmation` по уровню для сравнения выбранных методов;
- H1 как основной timeframe поиска уровней;
- M1 как эталонный detail timeframe;
- касание уровня wick-ом;
- подтверждение закрытыми свечами после касания;
- вход на открытии следующей detail-свечи;
- несколько независимых вариантов SL/TP;
- комиссии и slippage;
- расчёт realized net PnL;
- сводная статистика по каждому варианту;
- deterministic unit/integration tests.

В первую версию не входят:

- live-торговля;
- HTTP/WebSocket fallback из `precision_grid_v2`;
- trailing stop;
- breakeven;
- partial exit;
- автоматический подбор оптимальных параметров;
- машинное обучение;
- переписывание frontend на React/Vue/Svelte;
- обязательное подключение Vite.

## 4. Методы подтверждения входа

В текущий этап входят только три метода из `MVP_1H`:

| Номер | ID | Правило |
|---|---|---|
| 1 | `touch` | вход после подтверждённого касания уровня |
| 3 | `consecutive` | `N` последовательных закрытий за уровнем в сторону сделки |
| 5 | `bounce` | `N` последовательных направленных свечей с закрытием за уровнем |

Метод 2 и метод 4 пока не реализуются. Методы выбираются списком и получают
одинаковые уровни и touch-события.

### 4.1. Эталонное определение отскока

### 4.2. Касание

Для поддержки:

```text
candle.low <= level.price
```

Для сопротивления:

```text
candle.high >= level.price
```

Касание определяется по wick, а не по close. Сначала используется H1-событие
`level.touched`, затем оно уточняется по detail-свече, если доступны detail
данные.

### 4.3. Подтверждение отскока

Для LONG от поддержки подтверждающая свеча должна быть:

```text
candle.close > candle.open
and candle.close > level.price
```

Для SHORT от сопротивления:

```text
candle.close < candle.open
and candle.close < level.price
```

Требуется `required_bars` последовательных подтверждающих свечей. Значение по
умолчанию: `2`.

Касание считается завершённым до начала отсчёта подтверждающих свечей. Сама
свеча касания не является первой подтверждающей свечой.

Поле `price_probed`, аналогичное `precision_grid_v2`, может сохраняться как
диагностическая информация, но не является обязательным условием входа.

### 4.4. Время и цена входа

После закрытия последней подтверждающей свечи:

- `entry_time` = `open_time` следующей detail-свечи;
- `entry_price` = `open` следующей detail-свечи;
- если следующей свечи нет, setup остаётся `unresolved` и сделка не создаётся.

Это соответствует текущему `entry_on_next_bar: true` в
`domain/confirmation/models.py`, но правило должно быть покрыто тестом.

### 4.5. Таймаут

Если после touch не набрано `required_bars` до `max_wait_bars`:

- setup получает статус `cancelled` или `expired` согласно утверждённому
  правилу;
- сделка не создаётся;
- событие содержит причину и количество просмотренных свечей.

Для исторического replay таймаут считается только в detail-барах. Wall-clock
таймеры из live-проекта не используются.

## 5. Конфигурация эксперимента

Конфигурация должна быть разделена на общую конфигурацию replay/входа и список
execution-вариантов.

Пример целевого формата:

```yaml
experiment:
  name: bounce_sl_tp_grid_v1
  entry:
    method: bounce_confirmation
    timeframe: 1m
    required_bars: 2
    max_wait_bars: 15
    entry_on_next_bar: true
  execution:
    fee_percent: 0.04
    slippage_percent: 0.01
    intrabar_policy: stop_first
    position_sizing: fixed_risk
    risk_per_trade: 1.0
    variants:
      - id: sl_02_rr_2
        name: SL 0.2% / RR 2
        stop:
          type: percent_from_entry
          value: 0.2
        take:
          type: risk_reward
          value: 2
      - id: sl_03_rr_2
        name: SL 0.3% / RR 2
        stop:
          type: percent_from_entry
          value: 0.3
        take:
          type: risk_reward
          value: 2
      - id: sl_05_tp_1
        name: SL 0.5% / TP 1%
        stop:
          type: percent_from_entry
          value: 0.5
        take:
          type: percent_from_entry
          value: 1.0
```

Проценты в конфигурации пользователя задаются как `0.2` для 0.2%, а не как
`0.002`. Внутри домена значения должны быть `Decimal` и нормализоваться явно.

Каждый вариант обязан иметь стабильный `id`. Конфигурация эксперимента должна
сохраняться вместе с run и входить в `config_hash`.

## 6. Правила SL/TP

### 6.1. Варианты первой версии

Реализовать следующие правила:

| Rule type | Расчёт |
|---|---|
| `percent_from_entry` | расстояние от цены входа в процентах |
| `risk_reward` | TP = фактический риск до SL × RR |

Направление:

- LONG: SL ниже entry, TP выше entry;
- SHORT: SL выше entry, TP ниже entry.

Цена SL/TP округляется по `tick_size` инструмента. После округления необходимо
повторно проверить, что SL и TP находятся по правильную сторону от entry.

### 6.2. Следующий этап расширения

После проверки процентных вариантов добавить отдельными задачами:

- `stop_beyond_level`;
- `stop_beyond_zone`;
- `take_percent_from_entry`;
- `take_structural_level`;
- несколько take-профитов;
- breakeven;
- trailing;
- partial exit.

Эти правила нельзя добавлять в первую матрицу одновременно с базовой
реализацией: сначала должна быть подтверждена корректность fixed SL/TP.

## 7. Модель домена

### 7.1. ExecutionVariant

Добавить неизменяемую модель варианта исполнения, например в
`domain/execution/models.py`:

```text
ExecutionVariant
- id
- name
- stop_rule
- stop_value
- take_rule
- take_value
```

Комиссия, slippage, intrabar policy и position sizing относятся к конфигурации
эксперимента, если они одинаковы для всех вариантов. Если в будущем они станут
частью варианта, это должно быть явно отражено в `variant_id`.

### 7.2. Trade

Расширить `Trade` полями:

- `variant_id`;
- `quantity`;
- `notional`;
- `risk_amount`;
- `gross_pnl`;
- `fees`;
- `slippage_cost`;
- `net_pnl`;
- `r_multiple`;
- `unresolved`.

Текущее поле `pnl` можно сохранить как compatibility alias только если это
нужно существующим API. Новым кодом использовать явно `net_pnl`.

### 7.3. Независимое исполнение

Рекомендуемая структура:

```text
shared setups
  -> for each execution variant:
       clone/evaluate independent trade state
       calculate independent exit
       calculate independent result
```

Нельзя переиспользовать один объект `Trade` между вариантами. Нельзя позволять
закрытию сделки варианта A менять setup, уровень или сделку варианта B.

## 8. Исполнение свечей

Для каждой открытой сделки рассматриваются только detail-свечи:

- после `entry_time`;
- с `close_time <= current replay cursor`;
- в хронологическом порядке.

Для первой версии принять консервативную политику `stop_first`:

- если одна свеча достигает и SL, и TP, результатом является SL;
- exit price равен цене соответствующего bracket после tick rounding;
- выходной slippage должен учитываться явно, а не только при открытии.

Текущий `TradeExecution._exit_reason()` проверяет SL раньше TP. Это поведение
нужно сохранить только после добавления отдельного параметра и теста, а не
оставлять неявным.

Сделка, остающаяся открытой на `effective_to`, получает статус `unresolved`.
Она не включается в realized net PnL, но входит в отдельный счётчик и отчёт.
Искусственно закрывать её последней ценой в первой версии нельзя.

## 9. Размер позиции и метрики

### 9.1. Размер позиции

Кодер не должен молча выбирать формулу размера позиции. До реализации матрицы
необходимо зафиксировать режим.

Рекомендуемый основной режим для сравнения SL/TP:

```text
fixed_risk
quantity = risk_per_trade / abs(entry_price - stop_price)
```

Дополнительно желательно поддержать `fixed_notional`, чтобы сравнивать
результаты в двух режимах. Для каждого run режим sizing сохраняется в
конфигурации.

### 9.2. Обязательные результаты по варианту

Для каждого `variant_id` рассчитать:

- total setups;
- entered trades;
- closed trades;
- unresolved trades;
- winning trades;
- losing trades;
- gross PnL;
- total fees;
- net PnL;
- win rate;
- average net PnL;
- expectancy;
- profit factor;
- total risk;
- average `R`;
- max drawdown.

Главная денежная метрика:

```text
net PnL = сумма gross PnL - комиссии - slippage costs
```

Положительным считается вариант с `net PnL > 0`, но лучшим нельзя автоматически
считать вариант только с максимальным PnL. В отчёте обязательно показывать
количество сделок, drawdown и profit factor.

Качество реакции уровня (`Outcome`) и торговый результат (`TradeResult`) должны
оставаться разными сущностями. Успешный отскок не обязан означать прибыльную
сделку при каждом SL/TP.

### EXP-005. Aggregate evaluator

Задачи:

- рассчитать drawdown, expectancy и profit factor;
- не смешивать `Outcome` и `TradeResult`.

Критерии готовности:

- сумма сделок совпадает с aggregate net PnL;
- результат по варианту воспроизводим;
- вариант с нулём сделок не ломает отчёт;
- комиссии отражаются в net PnL.

### EXP-006. Replay integration

- передать одинаковый список setups во все варианты;

  финального завершения run;
- расширить snapshot результатами вариантов.

Критерии готовности:

- одинаковое число setups у всех вариантов;
- разные SL/TP меняют только execution/trade results;
- restore checkpoint даёт ту же matrix результатов, что и непрерывный replay.

### EXP-007. Persistence

Задачи:

- расширить схему для experiment config;
- сохранить execution variants;
- сохранить setups;

- сохранить aggregate variant results;

- реализовать восстановление run и результатов.

Минимально необходимые связи:

```text
run -> experiment
experiment -> execution_variants
run -> setups
setup -> trades

run -> variant_results
```

Критерии готовности:

- после перезапуска процесса результаты не теряются;
- результат можно связать с run, setup, level и variant;

## 13. Итоговый критерий готовности этапа

Этап считается реализованным, если система может:

1. воспроизводимо найти уровни на заданном периоде;
2. определить touch и подтверждённый отскок только по доступным свечам;
3. создать одинаковый набор setups для всех вариантов;
4. провести независимые виртуальные сделки;
5. применить разные SL/TP;
6. корректно обработать SL, TP, комиссии, slippage и unresolved;
7. рассчитать net PnL и статистику по каждому варианту;
8. сохранить конфигурацию и результаты;
9. показать, какой вариант дал положительный совокупный результат;
10. доказать тестами отсутствие lookahead и изменение результата из-за порядка
    перебора вариантов.
