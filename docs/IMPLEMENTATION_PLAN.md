# Levels Tester: план реализации

## 1. Назначение

Levels Tester — браузерный интерактивный исторический replay-тестер для
оценки торговой системы уровней на Binance USDT-M Futures.

Пользователь выбирает символ и дату начала. Система загружает исторические
свечи, воспроизводит рынок от начала периода до последней закрытой свечи,
пошагово ищет пивоты и уровни и показывает их на графике.

H1 используется как основной таймфрейм поиска уровней. M5 или M1 используются
для детализации касаний, подтверждения входа и исполнения сделки.

Проект является историческим replay, а не live-торговым приложением. Текущие
данные могут загружаться до последней закрытой свечи, но граница конкретного
запуска фиксируется для воспроизводимости.

## 2. Основные принципы

1. Алгоритм не имеет доступа к свечам правее текущей позиции replay.
2. Текущая незакрытая свеча не участвует в расчётах.
3. Историческое время отделено от wall-clock времени приложения.
4. Состояние уровня изменяется только через определённые события.
5. Один replay является каноническим источником времени для всех вариантов
   анализа.
6. Конфигурация, версия алгоритма и набор данных сохраняются вместе с запуском.
7. Доменное ядро не зависит от FastAPI, MariaDB и графического интерфейса.
8. Повторный запуск с теми же входными данными должен давать тот же результат.

## 3. Технологии

- Python 3.11+.
- FastAPI для HTTP API.
- WebSocket для последовательности событий и обновления состояния клиента.
- Vanilla JavaScript и lightweight-charts для первого интерфейса.
- MariaDB для свечей, запусков, уровней, событий и результатов.
- SQLAlchemy 2 для доступа к БД.
- Alembic для миграций.
- Pydantic Settings для типизированных runtime-настроек.
- YAML для не секретных параметров алгоритма.
- Переменные окружения для секретов и подключения к БД.

Vite не является обязательным для первого прототипа. Его следует добавить,
если появится реальная потребность в TypeScript или сложной сборке frontend.

## 4. Границы первого релиза

В первый релиз входят:

- один выбранный Binance USDT-M инструмент;
- таймфрейм поиска уровней H1;
- выбор даты начала;
- автоматическое завершение на последней закрытой H1-свече;
- загрузка и хранение H1 и M1/M5 свечей;
- causal-поиск pivot points и уровней;
- отображение свечей, пивотов, зон и событий уровня;
- play, pause, resume, step, reset и изменение скорости;
- одно окно H1 и одно окно детализации M1/M5;
- один или несколько outcome-профилей на общем replay;
- сохранение запуска и результатов.

Не входят в первый релиз:

- реальная торговля и отправка ордеров;
- автоматический подбор лучшей стратегии;
- несколько независимых replay-движков для разных вариантов;
- многопользовательская авторизация;
- поддержка других бирж;
- отдельный desktop-клиент.

## 5. Временная модель

У запуска есть четыре разных временных значения:

- `display_from` — дата, с которой пользователь видит график;
- `calculation_from` — начало истории для расчёта warm-up;
- `effective_to` — зафиксированная последняя закрытая свеча;
- `cursor_time` — текущая позиция replay.

`calculation_from` должен быть раньше `display_from`. Warm-up рассчитывается
из максимального lookback алгоритма, pivot wing, validation window и периода
подтверждения входа.

Все timestamps хранятся в UTC. Интервал периода должен иметь однозначное
правило границ: `from` включительно, `to` исключительно либо включительно;
это правило фиксируется в API и тестах.

Pivot с правым wing становится доступным только после появления и закрытия
необходимого числа правых свечей. В объекте pivot сохраняются `pivot_time` и
`confirmed_time`.

Уровень получает отдельные времена:

- `created_time`;
- `confirmed_time`;
- `broken_time`;
- `expired_time`, если используется срок жизни.

Время исходной точки pivot не должно использоваться как время появления уже
готового уровня.

## 6. Спецификация алгоритма

До реализации UI необходимо зафиксировать единственный вариант правил:

- поиск локального максимума и минимума;
- размер pivot wing;
- обработка равных экстремумов;
- фильтр объёма;
- объединение pivot в уровень;
- расчёт цены уровня и ширины зоны;
- минимальное количество касаний;
- минимальный отскок;
- правило touch;
- правило breakout: wick, close или оба условия;
- правило повторного касания;
- срок жизни уровня;
- запрет повторного входа или cooldown;
- правила подтверждения входа;
- правила отмены подтверждения;
- источник цены входа;
- правила исполнения stop, TP, trailing, breakeven и partial exit.

Текущий проект нельзя переносить как единый источник этих правил: в нём
`events.py`, `levels.py`, `validator.py` и `backtest.py` используют частично
различающиеся определения touch и breakout. Старые правила должны быть
сначала сравнены и утверждены как отдельная спецификация.

## 7. Состояние уровня

Уровень реализуется как конечный автомат. Минимальные состояния:

```text
CREATED
CONFIRMED
WAITING_TOUCH
TOUCHED
WAITING_ENTRY_CONFIRMATION
ENTRY_CONFIRMED
IN_TRADE
REBOUND
BROKEN
EXPIRED
```

Каждый переход обязан иметь:

- timestamp свечи;
- cursor sequence;
- причину перехода;
- ссылку на уровень;
- параметры, использованные при расчёте.

Статус `ACTIVE` не является историческим источником данных. Он вычисляется
внутри конкретного replay и отражает состояние уровня именно на текущем
cursor.

## 9. Replay engine

Replay engine должен быть детерминированным и пошаговым:

```text
for closed_h1_bar in chronological_bars:
    advance_cursor()
    confirm_available_pivots()
    update_level_states()
    emit_level_events()
    evaluate_entries()
    evaluate_positions_on_m1_or_m5()
    run_outcome_evaluators()
    emit_snapshot_and_events()
```

Скорость влияет только на интервал выдачи событий, но не на расчётный
результат.

Управление запуском:

- `play` — продолжить автоматическое продвижение;
- `pause` — остановить продвижение без потери состояния;
- `step` — обработать один следующий master-bar;
- `reset` — вернуться к началу запуска;
- `cancel` — завершить запуск без продолжения;
- `speed` — изменить скорость выдачи событий.

Состояния запуска:

```text
CREATED
LOADING
READY
PLAYING
PAUSED
COMPLETED
FAILED
CANCELLED
```

## 10. Таймфреймы

H1 является master timeline для поиска пивотов и уровней.

M1 или M5 являются execution/detail timeline. Их свечи доступны движку
только в пределах исторического времени, уже достигнутого replay.

Если внутри H1-свечи требуется точная последовательность событий, используется
M1. Если достаточно менее точного исполнения, можно выбрать M5. Политика
выбирается параметром запуска и сохраняется в БД.

Внутрисвечная неоднозначность должна иметь явную политику:

- `m1_exact` — использовать M1;
- `conservative` — выбирать худший допустимый исход;
- `optimistic` — только для исследовательского сравнения;
- `heuristic` — фиксированное правило порядка OHLC.

Для оценки торговой системы основной политикой является `m1_exact`.

## 11. Outcome-профили

Outcome-профиль — отдельный компонент, который получает общий поток событий
и оценивает уровень или сделку по собственной конфигурации.

Профиль может менять:

- срок ожидания отскока;
- глубину требуемого отскока;
- правило breakout;
- условия успешной обработки;
- условия неудачи;
- правила повторного касания.

Если профиль меняет сам поиск уровней или правила входа, это уже другая
стратегия и отдельный запуск, а не просто вариант outcome.

В первой версии несколько профилей показываются на одном графике разными
слоями и в сравнительной таблице. Отдельные N окон добавляются только после
проверки общего движка.

## 12. Хранение данных в MariaDB

Минимальные сущности:

```text
instruments
candles
data_ranges
runs
replay_checkpoints
levels
level_events
level_touches
outcome_profiles
outcomes
```

### instruments

Хранит exchange, market type, symbol, quote asset, статус инструмента, даты
листинга и закрытия, tick size и quantity step.

### candles

Хранит instrument, timeframe, open time UTC, close time, OHLCV, статус
закрытости и источник данных.

Уникальный ключ: `(instrument_id, timeframe, open_time)`.

### runs

Хранит symbol, display range, calculation range, effective end, cursor,
статус, настройки, версию алгоритма, hash конфигурации и идентификатор
набора данных.

### levels и level_events

Хранят экземпляр уровня конкретного запуска и полную историю его жизненного
цикла. Нельзя использовать одну глобальную запись уровня для всех запусков.

### outcomes

Хранит результат конкретного профиля для конкретного уровня/касания/сделки.

JSON используется только для расширяемых metadata. Основные поля, по которым
строятся фильтры и статистика, должны быть отдельными колонками.

Для цен и объёмов необходимо выбрать единый способ точности: DECIMAL с
инструментной precision либо масштабированные целые значения. Сравнение цен
через неокруглённый float запрещается.

## 13. Загрузка данных

Data ingestion service должен:

1. Получить или обновить metadata инструмента Binance.
2. Рассчитать необходимый диапазон H1 и M1/M5 с warm-up.
3. Загрузить данные пакетами с учётом API limit.
4. Выполнить upsert по уникальному ключу свечи.
5. Проверить сортировку, дубли, OHLC-инварианты и пропуски.
6. Не интерполировать пропущенные свечи молча.
7. Сохранить состояние загрузки и фактический диапазон.
8. Перевести run в `READY` только после успешной проверки данных.

Загрузка должна быть идемпотентной: повтор операции не создаёт дубликаты и
не портит уже загруженные свечи.

При сетевых ошибках применяются retry с backoff, обработка rate limit и
сохранение прогресса пакетной загрузки.

## 14. API

### Управление запуском

- `POST /api/runs` — создать запуск;
- `GET /api/runs/{run_id}` — получить состояние;
- `POST /api/runs/{run_id}/play`;
- `POST /api/runs/{run_id}/pause`;
- `POST /api/runs/{run_id}/step`;
- `POST /api/runs/{run_id}/reset`;
- `POST /api/runs/{run_id}/cancel`;
- `PATCH /api/runs/{run_id}/speed`;
- `GET /api/runs/{run_id}/snapshot`;
- `WS /api/runs/{run_id}/events` — snapshots и события.

REST используется для команд, WebSocket — для доставки событий и snapshot.
Это упрощает идемпотентность команд и восстановление после разрыва соединения.

Каждое событие имеет `run_id`, `sequence`, `event_time`, `event_type` и
payload. При reconnect клиент запрашивает snapshot и события после последнего
известного sequence.

- выбор символа;
- дату начала;
- выбор M1/M5;
- поле скорости;

- таблицу активных уровней;
- журнал событий;

Frontend не вычисляет торговую логику. Он отображает состояние, полученное

## 16. Отказоустойчивость

Обработать следующие случаи:

- Binance API недоступен;
- API вернул rate limit;
- в данных есть пропуски;
- БД недоступна во время загрузки;
- данные повреждены;
- процесс завершился во время replay;
- WebSocket разорван;
- команда pause/resume отправлена повторно;
- клиент подключился после нескольких событий;
- запуск повторно создан с теми же параметрами.

Checkpoint сохраняется на паузе, при завершении и периодически во время
длинного replay. При восстановлении engine продолжает с последнего
согласованного cursor.

## 17. Логирование и диагностика

Логи должны быть структурированными и включать:

- request id;
- run id;
- symbol и timeframe;
- cursor time и sequence;
- версию алгоритма;
- переход состояния run;
- переход состояния уровня;
- диапазон загруженных данных;
- ошибки Binance и MariaDB;
- количество пропусков и дублей.

Каждый важный результат должен быть объясним по журналу событий. Нельзя
использовать `datetime.now()` как историческое время события.

Не следует логировать API-ключи, пароли и полные URL с секретными параметрами.

## 18. Безопасность

- Публичные klines Binance не требуют торговых API-ключей.
- Ключи, если они понадобятся позже, хранятся только в environment/secret
  storage.
- Данные подключения к MariaDB не хранятся в Git.
- TLS-проверка должна быть включена.
- SQL выполняется через SQLAlchemy parameters.
- Символ, даты, скорость и профиль валидируются на API-границе.
- Сервер разработки по умолчанию слушает localhost.
- CORS и WebSocket origins ограничиваются явно.
- UI не имеет возможности произвольно изменять файлы конфигурации или выполнять
  SQL.

## 19. Тестирование

### Unit

- pivot не появляется раньше подтверждения правым wing;
- обработка равных экстремумов;
- кластеризация pivot;
- разделение support и resistance;
- touch и breakout;
- переходы автомата уровня;
- повторные касания и cooldown;
- M1/M5-синхронизация;
- intrabar policy;
- outcome-профили;
- расчёт позиции и exit;
- timezone и границы диапазона.

### Property и regression

- одинаковые входные данные дают одинаковые события;
- replay не читает будущее;
- скорость не меняет результат;
- pause/resume эквивалентен непрерывному запуску;
- восстановление из checkpoint эквивалентно непрерывному запуску;
- повторная загрузка свечей идемпотентна.

### Integration

- MariaDB migrations;
- upsert и уникальность свечей;
- обнаружение пропусков;
- mock Binance API и pagination;
- создание и восстановление run;
- WebSocket sequence/reconnect.

### End-to-end

- создать run;
- дождаться `READY`;
- запустить, поставить на паузу, продолжить;
- сделать step;
- получить пивот и уровень на графике;
- открыть detail M1/M5;
- завершить run и открыть результат.

Особое внимание уделяется тестам, где неправильный результат внешне выглядит
правдоподобно: lookahead, пробой внутри свечи, неправильное время pivot,
неверная граница периода и рассинхронизация H1/M1.

## 20. Производительность

Реальные потенциальные узкие места:

- загрузка большого объёма M1;
- повторное построение уровней по всей истории на каждом баре;
- отправка каждой свечи отдельным WebSocket-сообщением;
- запуск независимого engine для каждого варианта;
- отсутствие индексов в MariaDB.

Первоначальные решения:

- инкрементальное обновление состояния;
- пакетная выдача событий;
- запрос только видимого диапазона для графика;
- один общий replay для outcome-профилей;
- индексы по instrument/timeframe/open_time.

Не добавлять заранее микросервисы, multiprocessing, TimescaleDB или сложный
event sourcing. Сначала измерить реальные узкие места.

- старую визуализацию уже рассчитанного backtest;
- не подтверждённые статистические вероятности strength/bounce.

## 22. Порядок разработки

### Этап 0. Спецификация

Утвердить временную модель, состояния уровня, правила touch/breakout, вход,
исполнение и outcome-профили.

### Этап 1. Golden fixtures

Создать маленькие вручную проверенные наборы H1 и M1-свечей с ожидаемыми
pivot, level, touch, breakout и outcome.

### Этап 2. MariaDB и ingestion

Создать миграции, repositories, Binance adapter, upsert свечей, проверку
качества и data ranges.

### Этап 3. Domain engine

Реализовать causal pivot detector, level state machine и event generation без
FastAPI и UI.

### Этап 4. Replay

Добавить cursor, step, play/pause, reset, speed, checkpoint и восстановление.

### Этап 5. Entry/execution/outcomes

Добавить подтверждение входа, M1/M5 execution policy, SL/TP, trailing,
breakeven, partial exit и outcome evaluators.

### Этап 6. API

Добавить создание run, snapshot, команды управления, WebSocket и reconnect.

### Этап 7. Базовый UI

Отобразить H1-свечи, пивоты, уровни, события и управление replay.

### Этап 8. Detail timeframe

Добавить синхронизированное M1/M5-окно.

### Этап 9. Сравнение вариантов

Добавить несколько outcome-профилей, слои графика и таблицу сравнения.

### Этап 10. Hardening

## 23. Контрольные точки

Перед переходом к следующему этапу проверять:

1. После спецификации: нет неоднозначных переходов уровня.
2. После fixtures: результаты совпадают с ручным расчётом.
3. После ingestion: повторная загрузка не создаёт дубли, пропуски видны.
4. После domain engine: нет lookahead, pivot появляется только после right wing.
5. После replay: pause/resume и checkpoint дают тот же результат, что и полный
   непрерывный прогон.
6. После execution: однозначно обрабатываются SL/TP внутри одной свечи.
7. После API: reconnect и повтор команд не ломают состояние.
8. После UI: график показывает только события, доступные на текущем cursor.
9. После M1/M5: младший ТФ не показывает будущее относительно H1.
10. Перед исследованием: сохранены версия кода, конфигурация и набор данных.

## 24. Критерии готовности первой версии

Первая версия считается пригодной для исследований, если:

- один символ воспроизводится от заданной даты до последней закрытой свечи;
- уровень появляется только после причинно допустимого момента;
- в replay не используется текущий snapshot ACTIVE/BROKEN;
- результат одинаков при повторном запуске;
- pause/resume/reset работают предсказуемо;
- M1/M5-события синхронизированы с H1;
- пропуски данных не скрываются;
- результат можно связать с конкретными свечами и событиями;
- каждый запуск можно восстановить или явно определить как невосстановимый;
- тесты покрывают lookahead, intrabar ambiguity и временные границы.
